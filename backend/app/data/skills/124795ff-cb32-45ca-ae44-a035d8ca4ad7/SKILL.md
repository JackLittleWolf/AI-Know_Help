# フロントエンド React & TypeScript コード改修・レビュー

React と TypeScript のフロントエンドコードに対して、**コード改修**または**コードレビュー**のいずれかに本スキルを使用する。プロジェクト固有のコーディング規約とベストプラクティスは、本スキル内の references に従う。

## 使用タイミング

- **コード改修**: コンポーネント・フック・API クライアント・型定義の新規作成・追記、画面追加、機能追加
- **コードレビュー**: React コンポーネント（.tsx ファイル）のレビュー、TypeScript コードの品質チェック（.ts ファイル）、フロントエンドコードの git 変更分析、コミット前のコードレビュー、リファクタリングの検証

---

## タスク別の実施手順

利用目的に応じて、次のいずれかの手順を実施する。

---

### タスク A: コードの改修（新規・追記・更新）

**いつ使う**: 要件や設計書に基づいてフロントエンドコードを新規作成する、または既存コードに追記・更新するとき。

| 手順 | 実施内容 |
|------|----------|
| A-1 | **対象の確定** - 改修する対象を特定する（例：新規画面の追加、既存コンポーネントの修正、API 関数の追加）。 |
| A-2 | **入力の確認** - 要件書・設計書（画面定義書・API 定義書）を確認し、仕様・表示・操作を把握する。 |
| A-3 | **参照の読み込み** - 対象の種別に応じて、下記「レビューチェックリスト」各観点の参照ファイルを読み、命名・コンポーネント構造・型・UI 実装規約のルールを把握する。 |
| A-4 | **実装** - references に沿ってコードを執筆する。コンポーネントは単一責任、型は明示、スタイルは index.css 集約・constants/colors 利用に従う。 |
| A-5 | **自己チェック** - 改修した範囲について、下記「レビューチェックリスト」のクイックチェックを適用し、重大な規約違反がないか確認する。必要なら修正する。 |

- 複数ファイルを同時に追加する場合は、型定義 → API クライアント → フック → コンポーネントの順で参照を確認しながら実装する。

---

### タスク B: コードのレビュー

**いつ使う**: 既存のフロントエンドコードが規約・ベストプラクティスに沿っているか確認し、指摘や修正案を出したいとき。

| 手順 | 実施内容 |
|------|----------|
| B-1 | **対象の確定** - レビューするファイルまたは git 変更範囲を特定する。 |
| B-2 | **初期分析** - 対象を読み、コンポーネントの目的・データフロー・依存関係・型定義を把握する。 |
| B-3 | **参照の読み込み** - 対象ファイル種別に応じて、下記「レビューチェックリスト」各観点の参照ファイルを読み、チェック観点を把握する。 |
| B-4 | **チェックリストの適用** - 下記「レビューチェックリスト」を順番に適用し、命名・コンポーネント構造・型・UI 実装規約・コメント・エラーハンドリングについて不整合・規約違反を洗い出す。 |
| B-5 | **レビューレポートの出力** - 重要度別（重大・警告・提案）に指摘をまとめ、ファイル:行参照と修正推奨事項を出力する。良い点も記載する。 |

- レビューレポートの形式は、下記「レビューレポートの生成」に従う。
- 詳細な流れは、下記「レビュープロセス」の 1. 初期分析 → 2. チェックリスト適用 → 3. レポート生成 を参照する。

---

## レビュープロセス

タスク B（レビュー）の際は、以下 1. 初期分析 → 2. レビューチェックリストの適用 → 3. レビューレポートの生成 の順で実施する。

### 1. 初期分析

対象ファイルを読み込み、以下を理解する：
- コンポーネントの目的と責務
- データフローと状態管理
- 依存関係とインポート
- 型定義

### 2. レビューチェックリストの適用

以下のカテゴリを順番にチェックする：

#### 命名規約
詳細は [references/naming-conventions.md](references/naming-conventions.md) を参照。

クイックチェック：
- コンポーネント：PascalCase（例：`MeetingCard.tsx`）
- フック：camelCase で `use` プレフィックス（例：`useMeetings.ts`）
- 変数・関数：camelCase
- 定数：UPPER_SNAKE_CASE
- API 関数：`fetchXxx`、`createXxx`、`updateXxx`、`deleteXxx`
- Props 型：`XxxProps`

#### コンポーネント構造
- 単一責任の原則
- 適切なコンポーネント構成
- フックの適切な使用
- 関心の分離

#### TypeScript の使用
- 適切な型アノテーション
- 正当な理由なく `any` 型を使用しない
- Props のインターフェース・型定義
- ジェネリクスの正しい使用

#### React ベストプラクティス
- 適切なフック依存配列
- 不要な再レンダリングの回避
- 正しいイベントハンドラーパターン
- 適切なエラーバウンダリー

#### コードコメント
詳細は [references/comment-checklist.md](references/comment-checklist.md) を参照。

クイックチェック：
- コンポーネントの目的が文書化されている
- 複雑なロジックに説明がある
- 公開関数に `@param` と `@returns` 付きの JSDoc がある
- Props の意味が明確でない場合にコメントがある
- interface/type に用途コメントがある（export 有無を問わない）
- interface/type の全フィールドに簡潔な説明コメントがある
- state（`useState` / `useReducer`）に簡潔な説明コメントがある
- const フィールドに簡潔な説明コメントがある

#### エラーハンドリング
API エラーパターンについては [references/exception-handling.md](references/exception-handling.md) を参照。

クイックチェック：
- API エラーが適切にキャッチされ表示される
- ユーザーフレンドリーなエラーメッセージ
- コンポーネントに適切なエラーバウンダリー

#### UI 実装規約（スタイル・クラス・定数）
詳細は [references/ui-implementation.md](references/ui-implementation.md) を参照する。レビュー時に対象が UI を含むコンポーネントなら必ず読み、以下をチェックする。

**方針・責務**
- 見た目は `index.css` の `@layer components` に集約し、コンポーネントでは**クラス名のみ**指定しているか
- 役割が分かるセマンティックなクラス名（`card-meeting`、`title-page` 等）を使っており、**長い Tailwind の羅列を避けているか**（必要なら index.css に新クラスを追加）
- 状態別の色・ボタン種別は **constants/colors.ts** の `STATUS_COLORS` / `PRIORITY_COLORS` / `BUTTON_VARIANTS` / `INPUT_COLORS`（および `TOAST_COLORS` 等）を参照しているか

**クラス・定数利用**
- ページ外枠に `page-container`、見出しに `title-page` / `title-section`、カードに `card` 系共通クラスを使っているか
- ボタンは `btn-primary` / `btn-secondary` または **BUTTON_VARIANTS** を利用しているか（インラインで `bg-green-600` 等を直書きしていないか）
- ステータス・優先度バッジは `StatusBadge` / `PriorityBadge` と **STATUS_COLORS** / **PRIORITY_COLORS** を使っているか
- 色はモランディパレット＋状態色（constants/colors.ts）に統一しているか

**レスポンシブ・アクセシビリティ**
- ブレークポイント `sm` / `lg` を考慮しているか。セクションに `aria-label` を付与しているか
- ボタンは submit でない場合 `type="button"` を明示しているか。アイコンのみの操作に `title` または `aria-label` を付与しているか
- 主要要素（フォーム・ボタン・リンク・モーダル・リスト項目等）に id が付与されているか。id は kebab-case かつページ/コンポーネントプレフィックスで一意か（詳細は ui-implementation.md の「7. 要素の id」参照）

新規画面・コンポーネント追加時は、ui-implementation.md の「新規画面追加時のチェックリスト」も満たしているか確認する。

### 3. レビューレポートの生成（タスク B 用）

以下の形式で結果を提供する：

```
## コードレビューサマリー

### 重大な問題（必須修正）
- [ファイル:行] 問題の説明と修正推奨事項

### 警告（修正推奨）
- [ファイル:行] 問題の説明と改善提案

### 提案（改善案）
- [ファイル:行] 最適化または機能強化のアイデア

### 良い点
- 適切に実装されたパターンや良い実践例
```

## レビューガイドライン

### 重要度レベル

**重大**：機能を破壊する、セキュリティ問題、コア規約違反
**警告**：コードスメル、保守性の問題、軽微な規約違反
**提案**：最適化、代替アプローチ、スタイルの好み

### ファイルタイプ別の重点領域

**コンポーネント（.tsx）**：
- コンポーネント構造と構成
- Props インターフェース設計
- 状態管理
- イベントハンドラー
- レンダリングロジック
- **UI 実装規約**：クラス名は index.css 集約・セマンティックなクラス・constants/colors の利用。長い Tailwind 直書きの有無。page-container / title-page / card 系 / BUTTON_VARIANTS の使用。アクセシビリティ（type="button"、aria-label、title）。

**フック（`use` プレフィックス付き .ts）**：
- フックルールの遵守
- 依存配列
- 戻り値の型
- 副作用の管理

**API クライアント（`api/` 内の .ts）**：
- 関数命名（`fetchXxx`、`createXxx` など）
- エラーハンドリング
- 型安全性
- リクエスト・レスポンス型

**型定義（`types/` 内の .ts）**：
- interface vs type の使用
- 命名規約
- 再利用性
- ドキュメント

**ユーティリティ（`lib/`、`utils/` 内の .ts）**：
- 純粋関数
- 型安全性
- ドキュメント
- テストカバレッジ

## 出力形式（タスク B）

常に以下を提供する：
1. レビューしたファイルのサマリー
2. 重要度別の問題数
3. ファイル:行参照付きの詳細な結果
4. 実行可能な推奨事項
5. 良い実践例に対する肯定的なフィードバック

フィードバックは建設的、具体的、実行可能なものにする。
